# tgiFlyDay: notes for Claude Code

Race and practice management for FPV drone racing (EDRL, Estonia). It replaces LiveTime and LiveFPV. The full spec lives in the "EDRL Race System — Spec" doc (https://claude.ai/artifact/5KhyU3nUmv4cqyBRqt8pGv); ask the user for anything it doesn't cover.

## Current state

MVP: unattended practice time manager. No timer, no video. Heat loop, pilot kiosk, English voice callouts and tones, spectator view, RD console.

## Next layers, in order

1. LapRF 8-Way over TCP (port 5403): laps per pilot, beep or spoken callout on each gate pass (configurable parts: spoken name, channel, lap number, position, lap time). Feed starts into `engine.recordHeatResult()` so the 2-missed-heats auto-drop switches on. Practice must keep running if the timer drops out.
2. OBS via its websocket API: record only the FPV quad-view feed, one file per heat; switch spectator scenes by a preset sequence tied to the race phase.
3. Cloud relay = live.edrl.ee (view only; never control from the internet).
4. Race-day formats: EDRL and FAI qualifying, letter mains, FAI double-elimination brackets, check-in and payment, model check.

## Rules for the code

- Zero runtime dependencies unless there's a strong reason. Node >= 22.18 runs `server/*.ts` directly via type stripping:
  erasable TypeScript only (no enums, namespaces or parameter properties) and imports with `.ts` extensions.
- Keep race logic in `server/engine.ts`, pure and driven by an injected clock, and test it in `server/engine.test.ts` (`npm test`).
- Screens are plain HTML + JS modules in `web/`, sharing `web/assets/common.js` and `web/assets/style.css`.
- The venue has no Wi-Fi: everything local is wired. It must work fully offline.
- The RD PC runs Windows. Keep `start.bat` working.
- English UI and callouts.

## Pilot photos

- `data/photos/<pilot id>.jpg` is the live photo; `data/photos/known/<base64url of lowercased callsign>.jpg` remembers it by name (main.ts: rememberPhoto / restorePhotos). After every API call, pilots without a photo whose name is remembered get it back, so `/api/join` and `/api/pilot/add` already answer with `photo` set. Deleting a pilot keeps the remembered copy; removing a photo deletes both.
- Kiosk photo step (kiosk.html): after joining or signing in, "Is this you?" for a remembered photo, else the webcam (getUserMedia, whole landscape frame, zoomed fully out where the camera allows, 1280 px). No camera or no permission: skipped silently.
- getUserMedia needs a secure context, and the kiosk is plain http on the LAN: kiosk.sh (Linux) and kiosk.bat / tgiFlyDay Kiosk.exe (Windows) start the browser with `--unsafely-treat-insecure-origin-as-secure=<RD URL>` and `--use-fake-ui-for-media-stream` (Firefox: insecure media prefs in user.js).

## Updates (GitHub)

- Repo: github.com/leedu0512-eng/tgi-flyday (public). `release/` holds the published update: `release/app/flyday.cjs` (server bundled from main.ts, version stamped via the `TGIFLYDAY_BUILD_VERSION` define) + `release/app/web/` + `release/version.json` (version, files with sha256). Build it with `node tools/publish.mjs`, then commit and push.
- Version stamps are `YYYY.MM.DD-HHMM` (local time), compared as plain strings. server/version.ts.
- Installed updates live in `versions/<version>/` next to the exe; `app.json` points at the newest (a legacy `app/` folder is still read). exe.ts runs its `flyday.cjs` (createRequire) when newer than the built-in version; on any error it falls back to the built-in main.ts. `--built-in` forces the built-in one. Nothing in use is ever renamed: Windows refuses (that broke the first scheme). No fs.watch on an installed update's pages for the same reason. Old version folders are tidied 10 s after start.
- POST /api/update (server/update.ts): latest commit via the GitHub API (falls back to `main` when rate-limited), then every file from raw.githubusercontent.com at that commit, sha256-checked, into versions/<v>, then app.json. Then relaunch with `--after-update` (no new windows; waits for the port) and exit. data/ is never touched. Node also trusts the OS certificate store (antivirus HTTPS inspection). Errors are reported with their cause (`why()`), shown on the restart cover.
- **Before every publish:** `npm test` and `node tools/smoke-test.cjs` (Playwright: clicks the kiosk's on-screen keys, the big screen flyout, change channel, Going home and the phone page like a pilot). Both must pass. Tests that type into inputs directly missed two kiosk breakages.
- The restart cover shows a progress bar: GET /api/update/progress (stage check / download with files done of total / restart); the page creeps on to 100 % while waiting for tgiFlyDay to answer again. `TGIFLYDAY_FAKE_UPDATE=1` (dev) walks through a fake update to see it.
- The restart item lives in the view picker (common.js `restart()`); test with TGIFLYDAY_UPDATE_API / TGIFLYDAY_UPDATE_RAW pointing at a fake server.
- Unattended updates (main.ts `updateNow`, shared with the Restart button): nothing outside can reach the RD PC (Flyday is not on the venue network), so it updates itself: every night between 03:00 and 05:00 local (once a night), and when Flyday's hello answers `update: true` (`Install.state.updateRequested`, not saved). Both only while practice is stopped and nobody is signed in; a Flyday request waits until then.

## Session end time

- No end time by default. The RD console's clock icon opens the Session end page (`timeView`): a time, quick picks on the half hour, **No end time**. POST /api/finish {time: "HH:MM"} → `engine.setFinish(epoch)` (the next time the clock shows it); `clock.finishAt`, cleared whenever practice stops. `engine.finishTick(now)` (each second from main.ts): `texts.finishWarn` at 30, 20, 10 min (only those still ahead); at the time, `clock.lastRound` and `texts.finishLastRound`: the round being flown finishes (`goToNextHeat` stops instead of starting a new round, `texts.finishDone`). In free flight, waiting, or in the changeover before a round's first heat: it stops now (`texts.finishNow`). Then a clean start (see below). Callout switch `sessionEnd`. The clock icon shows "→ 20:00" / "last round"; the big screen's header says "until 20:00" / "Last round".
- No "Back to heats" buttons: the session-time icon goes back to the heats (also Escape, or the open page's icon again).

## Goodbye

- Every end of practice says goodbye: thanks the pilots and asks them to leave the club cleaner than they found it (`sessionStop` for Stop session, `nightEnd` when "Still flying?" goes unanswered, `finishDone` / `finishNow` for the end time). Callout texts are capped at 200 characters. Saved wording that is still an old default follows the new default (`OLD_DEFAULT_TEXTS` in engine.ts); wording the RD edited stays.

## Compact heats

- `engine.compact()` only between heats (`heatIsLive()`: arming, running, free flight → refused, the button greys out). It packs every heat, the one up next too (loop order from it), then removes the empty heats and renumbers the rest 1, 2, 3… from the one up next (`config.heatCount` shrinks; the changeover is for heat 1). Laps already flown keep their old heat number. If anyone moved or a heat was renumbered it says `texts.heatsChanged` (callout `heatsChanged`), before the line-up. `clock.pauseAfter` (action `pauseAfter`, button "Pause after this heat" in the clock box) makes the next changeover start paused with its full time; its line-up is held until Resume (`lineupPending`). `to20` always sets 20 s, also when less is left.

## Club quads

- `config.clubQuads` (up to 8; name, fixed VTX channel, broken). Pilots on one have `Pilot.quad` = its name, so the shared-quad rules apply (never two in one heat). Kiosk name step: **I don't have my own quad** (`data-club`, pre-ticked when `known.json` says the name flew a club quad last time; /api/walkin takes `club`, else the remembered flag). `engine.walkIn(name, usual, club)` → `pickClubQuad()`: first working quad nobody is on, else the working one with the fewest pilots (random among ties) → `seatOnQuad()`: its channel in the first heat it fits. Signing in with their own quad lets the club quad go.
- RD console: Club quads page (quad icon, in use / working; orange when one is broken). `setClubQuads` (POST /api/club-quads): renames keep pilots, a new channel re-seats them, Broken or removed moves them to another club quad (`texts.clubQuadBroken`, said under the heatsChanged switch); none left: they wait without a heat. Club quads don't show in the Pilots page's Shared quads. Club-quad pilots keep their quad's channel: `assertNotClub` refuses setSlot, setHeatChannel and join (kiosk Change channel) for them. The RD can drag them to another heat on the heat board (movePilot: the quad's channel in that heat, refused where it's taken or a quad-mate flies), and they also move when their quad changes channel, breaks, or the RD drags them to another club quad (`assignClubQuad`, null = their own quad from now on). Compact and Empty keep them on the quad's channel.
- Drag and drop, RD console only: heat board grips (`data-drag` → `data-drop-heat/slot`, POST /api/move: empty slot = move, a pilot = swap; club pilots' quad mark is their grip; dropped in another heat they keep the quad's channel); Club quads page chips (`data-drag-club` → a quad row or the "own quad" zone, POST /api/club-quad/assign). Re-renders wait while dragging (`dragging`). The phone page shows the club quad and who shares it. The big screen puts a small orange quad mark (`.club-q`, `clubMark()` in screen.html) before a club-quad pilot's name on the plates and the next-heat board.

## End of the day

- From `config.nightStopAt` (default 20:30 local; practice is usually 17:30–20:00, some fly longer) until 05:00, a running session asks "Still flying?" (`engine.nightTick`, fed local minutes by main.ts each second). The prompt is `nightPrompt(state, kind)` in common.js: big screen, console bar, phone card. "Yes, still flying" (POST /api/still-flying) snoozes it for an hour; no answer for 5 minutes → `endOfDay()`: stop and a clean start (see below). A session started late gets its first hour first. `config.nightStop` switches it off.

## Clean start

- Every automatic end of practice (end time: `finishSession`; unanswered "Still flying?": `endOfDay`) and the RD's **Reset for next time** (action `reset`, also stops a running session, no goodbye) call `engine.cleanSlate()`: every pilot deleted (remembered photos and usual channels stay), missed counts cleared, heats emptied, per-heat channel tweaks gone, heat length / changeover / heat count / channels back to `setupDefaults()`, clock counters, end time, snooze and pause-after cleared. Club quads, callouts, sound, timer settings and the lap history stay. **Stop session** by hand does not reset: the RD can stop, fix something and restart with the same pilots.
- `config.sessionDefaults` (null = built-in DEFAULT_CONFIG values) is set by **Save as defaults** in Session setup (action `saveDefaults`); each PC keeps its own. A saved copy that fails the checks (bad numbers, clashing channels) falls back to the built-in one. The line under the buttons (`#defaultsNote`) says what a clean start goes back to.

## Room lights

- The kiosk webcam doubles as a light meter (kiosk.html `lightCheck`, every 20 s, not when embedded in the big screen): a 320×240 stream kept open between photo steps (`lightStop()` before `startCamera()`), the picture's average luma on a 64×48 canvas, POST /api/light {level}. No picture leaves the kiosk. When it can't read, it posts {problem} instead (no camera API = page not opened through kiosk.sh / kiosk.bat with this RD PC's address; NotAllowed / NotFound / NotReadable; no picture yet) → `engine.lightProblem` → `light.problem` + `light.kioskAt`, shown in Session setup → More and the Online history card (nothing at all for 3 min: "isn't reporting"). A failed open retries after a minute. Opening the webcam and starting its picture each have a 10 s limit (`inTime`, `LIGHT_OPEN_MS`; one open at a time, `lightOpening`; a late answer is let go): on the HOBIzone Linux kiosk (12.11.2026) the light check went quiet after a while, most likely a webcam that never answered after the photo step had used it. A track that ended (unplugged, taken) is dropped and reopened. Tested by stubbing getUserMedia (answers once, then never). Testing it: Chromium honours `--unsafely-treat-insecure-origin-as-secure` only with its own profile (`--user-data-dir`) and not in Playwright's headless shell: use `launchPersistentContext(dir, { channel: 'chromium' })`.
- `engine.lightReading(level, now)`: below `config.lights.dark` (default 40) for `LIGHTS_OFF_AFTER_MS` (60 s) → off; one reading `LIGHT_MARGIN` (10) above the line → on (the first reading decides straight away); `lightTick` → unknown after 3 min without readings. `state.light` shows it; the console's Session setup → More has the switch, the dark line and the live reading.
- Lights off while practice runs (and `config.lights.enabled`): `night = { why: 'lights' }`, `texts.lightsOffAsk`, the usual "Still flying?" prompt; no answer in 5 min → `endOfDay()` (clean start, session.end reason `lights`). Lights back on, or a gate pass, cancels it. End of the day switched off doesn't cancel a lights question.

## Outbox (online history) and Flyday

- `server/outbox.ts`: engine `onEvent` → `data/outbox.jsonl` (one JSON row per line: id uuid, venue, at ISO, type, data). Types: `lights` {on, level}, `presence` {present true | false | null, why practice | activity | lights on | lights off | no clue, source, lights on | off | unknown, level, practice} (`engine.presenceNow`; Janno 12.11.2026: what matters is whether somebody is here, the lights are only a clue. Every clue counts: practice running = yes; somebody used tgiFlyDay (any POST except /api/light and /api/arm-measured → `noteActivity`) or a timed lap (`recordPass`) within `ACTIVE_MS` = 15 min = yes; else the kiosk webcam: lights on = yes, off = no; none = null. A row only when `present` changes (lightTick re-checks every second, so the 15 minutes running out is a change too), plus the start row and heartbeat; lights and practice ride along; `why` is in the outbox but not in the upload (schema 1 has no field for it), once at start (`source: start`: waits up to `PRESENCE_START_WAIT_MS` = 2 min after the first `lightTick` for the kiosk's first reading; a change sent before then counts as the first row) and every `PRESENCE_EVERY_MS` = 15 min since the last row, change or not (`source: heartbeat`), so Flyday can tell nobody there from tgiFlyDay off; `engine.presenceSent` = the last row, shown in the console's Online history card (`#oPresence`) with the kiosk webcam's reading), `session.start` {startedAt}, `session.end` {reason stop | endTime | night | lights | reset, startedAt, rounds, heatsRun, pilots (callsigns)}, `heat` (TimedRun + sessionStartedAt + passes: [{name, channel, clubQuad, passes (gate passes, server ms)}]). Events always collect, sending or not; sent rows move to `outbox-sent.jsonl`.
- Destination: the Flyday server (HOBIzone's). Only HOBIzone training sessions go there; Flyday decides by approving installs. Built-in base `https://hobizone.org/api/hz/tgiflyday/` (public, through Flyday's Cloudflare Tunnel), routes `hello` and `upload`. Private fallback `https://flyday.tail543cf5.ts.net:8445/api/hz/tgiflyday/` (tailnet only). `config.cloud.url` = the base set on this PC (empty = built in; `cleanServerUrl`: https only, any port, just the server gets the path, a trailing hello/upload is dropped, ends in /). `config.cloud.enabled` / `key` are no longer used (old saves).
- Pairing (`server/flyday.ts`, `Install`, `data/install.json`): install id (15 a-z0-9, = `tgiflyday_kiosk.id`), `install_secret` (kept on the PC; Flyday hands the token only to a hello carrying it), pairing code (e.g. `8TM-7JS`, from the secret; a `pairing_code` in Flyday's answer replaces it). `POST <base>hello` {install, install_secret, pairing_code, venue, pc, version} on start, every 10 min and on **Ask Flyday and send now**. Answers: `{status:"waiting"}` (also "too many waiting, try later"; optional `message`), `{status:"approved", token, send}`, `{status:"revoked"}`. Flyday controls only the upload (approve, send on/off, revoke, new token), never the racing. Secret and token never reach any screen (`publicInstall`).
- Upload (`toUploads`, schema 1): one body per row, `POST <base>upload` with `Authorization: Bearer <token>`: {schema 1, install, tgiflyday_kiosk {id, name, app_version}, session {id, started_at, ended_at, end_reason stop | end_time | night | lights | reset, timed} or null, pilots [{id, person: null, local_pilot, callsign, club_quad}], laps [{id, pilot, round, heat (1-based), free_flight, channel, lap (0 = holeshot, ms null in free flight), ms, crossed_at}], presence [{id, at, present, lights, practice, lights_note, kiosk_seen_at}]}. `lights_note` / `kiosk_seen_at` (portal agreed 13.11.2026): why there's no light reading (`engine.kioskNote`: the kiosk's own problem when it spoke in the last 3 min, else "the kiosk isn't reporting" / "hasn't reported since tgiFlyDay started"; null while the webcam reads), ≤ 120 characters, and when the kiosk last spoke (ISO or null, never junk: the portal answers `bad_date`). The admin's somebody-here tooltip shows it. Consecutive presence rows go in one body with session null; lights rows aren't sent. Ids are stable hashes (re-sends never duplicate): session by install + start time, pilot by session + name, `local_pilot` by install + lowercased name (the same typed name across sessions; linking to members comes later, `person` is always null for now), laps by heat + name + lap. Session notes (`SessionNote`: start, end, timed) are rebuilt from the sent log on start, so every upload carries the full session. Older heat rows (no passes) join the latest session started before them, laps from 1, no channel or crossing time.
- Answers (`verdictOf`; the public address is behind Cloudflare, which can answer by itself, so only the portal's own JSON `{"error": …}` counts): 2xx stored; 401 with `token_invalid` or `revoked` → token dropped, ask again with hello; 429 → busy backoff 1, 5, then 15 min (reset on success); 413 → halve the part and resend (`splitBody`; bodies are cut to ≤ 900 KB before sending anyway, `partsOf`, limit 1 MB; each part keeps the session and the pilots its laps need); other 4xx with the portal's JSON → stop and show it until Send now (`stopped`); anything else (other 401/403, HTML, 5xx, no answer) → again in a minute. A hello's `message` is plain text, shown with textContent, never as HTML.
- Console card **Online history**: pairing state and the code to approve in the Flyday admin, place name, Flyday address, Save, **Ask Flyday and send now** (POST /api/outbox/send: hello, then send).

## Windows Firewall

- `launch.ts` `firewallStatus(port)`: every connected network's kind (LAN and Tailscale can differ), firewall on, "block all incoming" (`AllowInboundRules False` → `closed`, the button can't help: the banner says which box to untick), program rules for `process.execPath` plus TCP port rules for PORT. `firewallAllow(port)`: one elevated PowerShell (RunAs) that removes the program's block rules (Windows adds them when its own "allow access" box is answered with the active network unticked, e.g. Public), then adds an allow rule for the program and one for the port, Profile Any; it writes `ok` or the error to a temp file, which goes back to the console's toast. Windows' own dialog is not the way: the banner says to use **Let them in**. Not testable outside Windows. On some PCs a normal (not admin) user can't read firewall rules ("access denied", seen at HOBIzone 12.11.2026): the check then answers `FW|denied` → null (no warning). And any request from another device (`reachedFromOutside` in main.ts, not loopback or this PC's own addresses) proves the way in is open: `firewallNow()` reports ok, and the console re-checks every 30 s while the warning shows. HOBIzone RD PC: its only network (Ethernet 2) is Public; fixed by hand with a TCP 8080 allow rule, Profile Any.

## Spectrum analyser (Janno 13.11.2026)

- Hardware: Waveshare ESP32-C5-WIFI6-KIT (U.FL antenna) with the ESPsoup firmware 0.7.1 (github.com/pit711/espsoup-firmware, GPL-3.0), on the RD PC's **native** USB socket (vendor 0x303a). We talk to the firmware with our own code only; nothing from the ESPsoup app (no licence).
- Reader `web/assets/spectrum.js` (browser module, runs only in the RD console opened on the RD PC itself: localhost = secure context, Web Serial). `startReader`: one tab at a time (`navigator.locks` 'tgiflyday-spectrum'); **Connect analyser** grants the port once (`requestPort`, filter 0x303a), after that `getPorts()` finds it again by itself. `hello`: "SYNC <n>" until echoed (up to 8 s, the board may be starting), "CAPS" must list SWEEP. "GAIN MANUAL <n>" (never automatic gain: levels jump). `planFor(channels)`: step centres every 20 MHz from the lowest channel − 20 to the highest + 20; the console always asks for all of L, R and F (5340–5960, 32 steps), so any viewer can switch to All channels at once; "SWEEP f0 f1 20 0 256 32" (rate 0 = 80 MS/s). Each step: "SWP <mhz> <nfft> <crc32 hex> <us>" + nfft int16 LE in 0.01 dB (−fs/2..+fs/2), crc32 (zlib) checked, damaged steps skipped; "END SWEEP"; "ERR …" throws. `stitch`: middle 20 MHz of each step, the 3 DC bins filled from their neighbours, floor = lower quartile, 1 MHz bins (linear mean) as dB above floor; `mirror` option if the real board turns out mirrored (not on by default). Posts {f0, db} to POST /api/spectrum at most about twice a second (or {problem}); the answer carries `enabled` and `gain` (config.spectrum, set on the Spectrum page from any console). Test: server/spectrum.test.ts against a simulated board.
- Server: `engine.spectrumReading` → `state.spectrum` {state connected|off, f0, db, channels: dB above floor per channel = linear mean within ±8 MHz (`spectrumLevels`), at, problem, readerAt}; `spectrumTick`: no sweep for `SPECTRUM_STALE_MS` (5 s) = off. /api/spectrum doesn't count as somebody using tgiFlyDay (presence).
- Spectrum page (console.html `drawSpectrum`, SVG; Janno 13.11.2026): the trace runs to scale underneath; each channel is a bar exactly as wide as the band its level is measured over (±8 MHz), red at ≥ `SPECTRUM_TAKEN_DB` (6). Toggle **Used channels** (the current heat's channels: config.channels with its per-heat changes, nothing hard-coded; label, MHz and dB above each bar) / **All channels** (all 24 L, R, F over 5340–5960, labels in three rows because R and F overlap; used ones outlined); per viewer (localStorage `tgiflyday.specAll`). Under each used channel: its pilot in the current heat, "signal, no pilot" / "no signal" (while flying). Controls: Connect analyser (RD PC only), Read the analyser (config.spectrum.enabled), Max hold (per viewer), Gain (config.spectrum.gain, default 48 until Janno says what looked right on the real board).
